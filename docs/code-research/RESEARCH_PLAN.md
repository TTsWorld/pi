# Pi 演进研究计划

## 研究摘要

**研究状态**：已完成。

**项目核心价值**：Pi 用一组明确分层的运行时边界，隔离模型供应方差异、通用工具循环、编程产品策略、终端渲染与会话持久化；用户获得的是有明确默认行为、又可通过扩展适配自身工作流的终端编程智能体。

**演进主线**：Pi 不是从今天的编程智能体逐步堆功能长成的。Git 可见的初始 `pi` 是 GPU Pod 与 vLLM 部署命令，配套的 `pi-agent` 才是今天产品的胚胎。系统随后经历三轮主要边界重构：多模型差异下沉到 `pi-ai`；通用循环与具体产品拆成 `pi-agent-core` 和 `pi-coding-agent`；长期会话继续向 `AgentHarness + Session v4 + 远程协议栈` 下沉。

**当前实现判断**：普通 `pi` 仍运行成熟的 `AgentSession + SessionManager v3 JSONL` 主链。Session v4、JSONL v4、SQLite、`pi-protocol`、`pi-client` 和 `pi-server` 已有真实实现，但生产级 `PiServerService` 尚不存在，`AgentHarness` 的提示、压缩、恢复与队列等关键执行路径仍明确返回 `HarnessNotImplemented`。因此当前是渐进迁移状态，不是新运行时已经替换旧运行时。

**设计亮点**：

1. 先用具体产品验证能力，再把跨场景能力下沉；浏览器、Pod 和 Slack 产品虽然迁出，推动形成的模型层、通用代理层和 SDK 仍然保留。
2. “极简”指少内置工作流，不是代码量少；计划模式、子代理和权限确认被外置到 Skills、Extensions 与 Pi Packages。
3. 本地 JSONL RPC 与远程 CBOR 协议服务于不同的一致性模型：前者控制一个本地 `AgentSessionRuntime`，后者面向可附着多个会话的远程服务。
4. 当前最重要的历史约束是双会话模型、双协议和模型兼容外观并存；修改产品行为时应先沿成熟 `AgentSession` 主链阅读，再进入实验性 Harness。

## 项目概述

**它是什么**：Pi 是一个以终端编程智能体为官方产品、以多模型智能体运行时为底座，并正在扩展持久化与远程会话能力的 npm 单仓多包项目。

**解决什么问题**：它把模型厂商差异、工具调用循环、长期会话、终端交互和产品扩展机制拆成独立边界，使编程智能体可以在不绑定单一模型、单一界面或固定工作流的情况下演进。

**谁在使用**：终端中的编程智能体用户、通过 SDK 或本地 RPC 嵌入 Pi 的开发者、编写 Extensions、Skills 和 Pi Packages 的扩展作者，以及正在接入实验性远程协议与持久会话栈的应用开发者。

## 研究范围与证据规则

- 只研究“系统如何演变”及“历史设计今天落在哪里”。
- 不扩展到完整架构、学习路径、Day 0 复原或代码质量评分。
- 历史结论必须来自目标仓库的 Git commit、diff、历史文件或 changelog。
- 当前实现结论必须回到 `origin/main` 的源码、类型、接口或调用链核对。
- 明确区分提交直接说明的事实、根据变更顺序得出的合理推断和无法从仓库确认的问题。
- 忽略测试、依赖目录、构建产物和锁文件；发布与测试基础设施只在解释分发演进时使用。

## 研究专题

### 专题 G：系统演进历史

- 目标：解释 Pi 的产品身份、模块边界、会话模型、扩展方式、供应方运行时和远程持久化能力如何被逐步推出来。
- 重点：初始 Pod 产品、`pi-ai` 抽取、`web-ui` 试验、通用核心与产品层拆分、`AgentSession`、Extensions、仓库收窄、`AgentHarness`、`pi-protocol`、`pi-client`、`pi-server`。
- 输出：`docs/code-research/07_evolution_history.md`

### 专题 H：实现地图

- 目标：把历史阶段映射到当前 package、公开接口、主调用链、会话存储和实验性远程路径，并解释每个边界为什么存在。
- 重点：成熟命令行主链与下一代持久化/远程栈的并存状态，以及由历史兼容留下的双会话模型、双协议和兼容外观。
- 输出：`docs/code-research/08_implementation_map.md`

## 验证检查

2. 实现地图中的每项核心能力至少落到一个当前源码文件和具体类型、函数或接口。
